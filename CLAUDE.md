# CLAUDE.md — ClawStack AI Pair Programming Guide

## Project Purpose

Build a unified agent runtime: multi-channel (Telegram, CLI, web), self-improving (trajectory → skill synthesis), with a built-in coding brain (repo-aware edit/test/verify loop).

**Core principle: Rust orchestrates, Python proposes.**
- Rust = authoritative, secure, production-critical
- Python = experimental, adaptive, learning layer

## Architecture

```
Channel → Gateway → Kernel (classify intent → enforce policy → execute) → ToolBus
                                     ↓
                    ┌────────────────┼────────────────┐
                    ↓                ↓                ↓
               Memory           Workers            Python
           (Postgres+pgvector)  (Docker/WASM)    Learning Service
                                                     ↓
                                              SkillSynthesizer
                                                     ↓
                                              SkillRegistry (Rust)
```

## Key Design Decisions

### 1. Tool Bus is the Single Execution Interface
Every tool — native Rust, WASM, Docker worker, MCP, Python endpoint — uses the same `ToolSpec` interface. This is intentional. The kernel never calls tools directly; it always goes through the bus.

### 2. Capabilities are Enforced at the Kernel, Not at the Tool
Tools declare required capabilities in their `ToolSpec`. The kernel checks `WorkspacePolicy` before dispatch. Tools SHOULD NOT check their own capabilities.

### 3. Python Never Blocks User Requests
Python runs async, offline, on a schedule. It proposes (`SkillDraft`) but Rust decides (`approve_skill`). No Python service is in the hot path.

### 4. Memory is Tiered
- Short-term: recent turns in Postgres
- Mid-term: session summaries (generated by Python, stored in Postgres)
- Long-term: pgvector embeddings for semantic retrieval

### 5. Trajectories are First-Class
Every multi-tool request is stored as a `Trajectory`. These feed the learning loop. Not optional.

## Rust Crate Conventions

- All types in `clawstack-common`
- Traits use `async_trait`
- Errors use `thiserror` + `ClawstackError` enum
- No `unwrap()` in library code
- `Arc<dyn Trait>` for trait objects in structs

## Python Conventions

- `async def` throughout
- Pydantic v2 for schemas
- Structlog for structured logging
- No sync I/O in request handlers

## Working with Schemas

Schemas live in `schemas/` as JSON Schema. These are the **source of truth**. If you change a type in Rust, update the JSON Schema. If you change the JSON Schema, regenerate Python types.

## Development Workflow

1. Clone + `docker compose up -d`
2. Make Rust changes → `cargo build`
3. Make Python changes → `cd python && uv sync`
4. Test via CLI: `cargo run -p clawstack-cli -- chat`
5. Check: `curl localhost:8080/health`
